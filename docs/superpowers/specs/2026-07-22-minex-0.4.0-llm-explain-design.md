# minex 0.4.0 design spec — LLM explanation of the minimal example

Date: 2026-07-22
Status: draft for review
Milestone: 0.4.0 (third of three: 0.2.0 core [done], 0.3.0 HDD [done], 0.4.0 LLM)
Depends on: 0.2.0 (run_code, matcher, minex_result), 0.3.0 (granularity = "expression")

## Goal

After minex reduces a failing script to its minimal reproducing snippet, add an
optional step that hands that snippet to a language model and returns a
structured, four-part account of the failure:

1. **Explain** — why the snippet fails, in plain English.
2. **Fix** — a corrected version of the snippet, *verified by executing it*.
3. **Bug report** — a paste-ready reproducible-example report.
4. **Diagnose** — the failure category and the R concept involved.

The LLM only ever sees the already-minimal snippet plus the recorded failure, so
no large-file encoding (graph/NN) is needed: reduction has already done the work
of making the input small and focused.

## Non-goals

- The LLM does **not** replace minex's oracle. "Does a reduction still reproduce?"
  remains a runtime fact proven by execution; the LLM is advisory only.
- No change to the deterministic reducer (`minex()`, `ddmin()`, HDD). This feature
  is a strictly additive, opt-in second step.
- No hard dependency on any LLM provider or on `ellmer`: the LLM feature is
  entirely `Suggests`-gated. (`explain_failure()` uses `utils::sessionInfo()`, so
  `utils` is added to `Imports` — a base-recommended package, always present; and
  `stats`, already used by 0.3.0 code, is declared too. Both fix an existing
  undeclared-`::` gap. No new *third-party* runtime dependency is introduced.)
- No rexgraph / relational-complex / hypergraph-NN integration (evaluated and set
  aside: the input is already minimal, and that stack is not CRAN-compatible).

## Architecture

### New function: `explain_failure()`

Separate from `minex()` so the reducer stays pure and deterministic (a network
call must not enter the core reduction path, nor pollute `minex_result`).

```r
explain_failure(x,
        chat = NULL,
        verify_fix = TRUE,
        timeout = 60,
        session_info = TRUE,
        modes = c("explain", "fix", "report", "diagnose"))
```

- `x` — a `minex_result` (carries `code`, `target$message`, `target$classes`,
  `condition`, `backend`). **No character-vector overload in 0.4.0** (YAGNI):
  `explain_failure()` pairs with `minex()`, whose output is a `minex_result`. `x` is
  validated as such and `explain_failure()` errors otherwise.
- `chat` — an injected `ellmer` Chat object (dependency injection; no vendor
  hard-wired). When `NULL`, read `getOption("minex.chat")`; if still absent, stop
  with actionable setup guidance. Works with any `ellmer` backend — local
  (`chat_ollama()`) or cloud. **Used statelessly:** `ellmer` Chat objects are
  mutable and accumulate turn history, so `explain_failure()` clones the Chat
  (`chat$clone()` when available) or issues a one-shot before use, so repeated calls
  never leak history into each other and `getOption("minex.chat")` acts as a
  template, not a shared conversation.
- `verify_fix` — when `TRUE` (default), execute the model's proposed fix in a
  fresh **`callr`** process (never in-process) and record whether it produces a
  clean run. A heuristic denylist first skips auto-execution of fixes containing
  obvious side-effecting calls (see Safety). `FALSE` disables all code execution
  (pure suggestion).
- `timeout` — seconds allowed for the sandboxed fix execution (default `60`).
  `minex_result` does **not** store a timeout, so `explain_failure()` owns this rather
  than reading a nonexistent `x$timeout`.
- `session_info` — include `utils::sessionInfo()` in the bug report (default
  `TRUE`; a real bug report needs it, but it can be omitted for privacy).
- `modes` — subset of the four sections to request (default all four). Note the
  one dependency: `"report"` embeds the explanation, so requesting `"report"`
  computes the explanation text even if `"explain"` is not separately in `modes`
  (an unrequested `explanation` *field* is still `NULL`, but the report contains it).
  All other modes are independent.

Returns a `minex_explanation` S3 object. `chat` is **duck-typed**, never
class-checked against `ellmer`'s R6 `Chat`: `explain_failure()` depends only on
`chat$chat_structured(prompt, type =)` (the structured result) and a model/provider
accessor for the `model` field. Any object exposing those two satisfies it, which is
what makes the stub in tests possible.

### Data flow

```
minex_result  ->  build_prompt(x, modes, session_info)
              ->  chat$chat_structured(prompt, type = explanation_type())   # ellmer
              ->  parse into minex_explanation fields
              ->  if verify_fix && "fix" in modes:
                    run_code(split_statements(fix$code), backend="callr",
                             timeout=timeout) -> fix$verified   # split first; always callr
              ->  assemble bug_report markdown
```

### The `minex_explanation` object

An S3 list with `print`, `format`, and `as.character` methods (mirroring
`minex_result`; `as.character` returns the bug-report markdown):

| Field | Type | Content |
|-------|------|---------|
| `explanation` | chr(1) | why the snippet fails |
| `diagnosis`   | list   | `category` (chr), `concept` (chr), `severity` (chr) |
| `fix`         | list   | `code` (chr), `rationale` (chr), `verified` (lgl or NA), `verification` (chr: what running it did) |
| `bug_report`  | chr(1) | assembled markdown (repro + error + explanation + optional sessionInfo) |
| `model`       | chr(1) | model/provider string from the Chat, for provenance |
| `modes`       | chr    | which sections were requested |

Sections not requested in `modes` are `NULL`. `fix$verified` is `NA` when
`verify_fix = FALSE`, when the fix run can't be observed, or for custom-oracle
results (see Fix verification for the full three-valued rule).

### Structured output, not prose parsing

The model is asked for a typed object via `ellmer`'s structured-output support
(`type_object()` / `chat_structured()`), so fields arrive already separated and
validated — no regex scraping of free text. This satisfies the project rule to
validate LLM outputs at the boundary. `build_prompt()` and `explanation_type()`
are small, independently testable helpers.

### Fix verification (the differentiator)

When a `fix` is requested and `verify_fix = TRUE`:

1. **Split then run.** `fix$code` is a single multi-line string, but `run_code`
   evaluates only the *first* top-level expression of each vector element (`R/oracle.R`),
   so it must first be split into statements exactly as `minex()` does:
   `run_code(split_statements(fix$code), backend = "callr", timeout = timeout)`.
   Without the split, a fix like `library(x)\n<real fix>` would run only `library(x)`,
   report a clean run, and falsely verify. Model-generated code is *never* executed
   in-process, regardless of `x$backend` (the in-process path has no isolation and no
   timeout); `explain_failure()` pins `callr` here unconditionally.
   The split-and-run is itself guarded: `split_statements()` calls `parse()`, which
   throws on syntactically invalid input (a truncated fix, an unbalanced brace), and
   that happens *before* `run_code`'s own `callr`/`tryCatch` engages. So a parse
   failure is caught and mapped to `fix$verified = NA` with `verification = "fix did
   not parse: <message>"`; the assembled explanation/diagnosis/bug_report are still
   returned (never abort the whole call over an unparseable fix).
   The concrete target condition/type is re-resolved from `x$target` via the same
   `pick_target_condition(x$target$conditions, x$condition)` minex used (so
   `condition = "any"` maps to the actual resolved type), and the matcher is rebuilt
   from `x$match` — never by reading `x$condition` directly.
2. Decide `fix$verified` on **cleanliness**, not on target-type presence, so no
   case is left unclassified. Call a run *clean* iff it is `observed` **and**
   produces no error of any type **and** no condition of the target's type:
   - `TRUE` iff the run is clean — the only honest basis for pasting a fix into a
     bug report as "verified".
   - `FALSE` iff the run is `observed` but **not** clean. This subsumes *every*
     not-clean outcome: the same target failure, a different error, or a fresh
     error of another type (e.g. a warning target whose fix now crashes). The
     matcher against `x$target` is used only to choose the `verification` wording
     (`"same failure still present"` vs `"different failure: …"`), never to decide
     TRUE/FALSE.
   - `NA` iff execution can't be observed (timeout/crash → `observed = FALSE`), with
     an explanatory `verification`. Never fabricate a check.
3. **Custom-oracle results** (`x$target = NULL`): the user's failure was defined by
   a function that `minex_result` does not store, so there is no reproducible check.
   Set `fix$verified = NA` with `verification` stating the oracle was not captured.
   Do **not** substitute a "ran cleanly" pass — a custom oracle may define failure
   as a non-error property (wrong value, specific warning), so cleanliness could
   contradict the user's actual definition.

This reuses 0.2.0 `run_code` and `split_statements` exactly as `minex()` does; the
only new choices are pinning `callr` and the denylist screen.

## CRAN and testing

- `ellmer` (and any provider package) go in **`Suggests`**. `explain_failure()` guards with
  `requireNamespace("ellmer")` and errors with install guidance if absent.
- **Every test that touches `ellmer` begins with `skip_if_not_installed("ellmer")`.**
  This includes the prompt/parse/pipeline tests and `explanation_type()` — the type
  helper builds a real `ellmer` type object, so it needs `ellmer` *installed* even
  when the Chat is stubbed. The stub replaces the *network/provider*, not the package.
- **Injectable Chat → deterministic tests.** Tests pass a *stub* Chat object whose
  `chat_structured()` returns canned structured data, so the prompt→parse→assemble→
  print pipeline runs with **no network and no API key**.
- **Fix-verification tests** exercise the real `callr` path (the only path `explain_failure()`
  uses): a known-good fix (clean run) → `verified = TRUE`; a fix that still errors
  (same or different error) → `FALSE`; a `verify_fix = FALSE` / custom-oracle /
  unobservable case → `NA`. `callr` is already an `Imports` dependency, so these run
  everywhere; the slow ones may be `skip_on_cran()`.
- Examples that need a real model are wrapped in `\dontrun{}`. One live
  round-trip test is `skip_on_cran()` + skipped when no model is configured.
- **Vignette.** minex ships a knitr vignette, which `R CMD check --as-cran`
  *rebuilds and evaluates* (under `_R_CHECK_DEPENDS_ONLY_`, only hard deps present).
  Any chunk demonstrating `explain_failure()` with a real model must be `eval=FALSE`
  (or guarded by `requireNamespace("ellmer") && nzchar(Sys.getenv(...))`); only
  stub-Chat, network-free chunks may evaluate. Otherwise the vignette build fails on
  CRAN (`ellmer` is Suggests-only, no key/network).
- Spelling: add any new technical words to `inst/WORDLIST`.

## Prompt design and safety

- **Prompt-injection defense.** The reduced code is untrusted input. The system
  prompt frames it explicitly as *data to analyze, not instructions to follow*,
  and the structured-output contract constrains the response shape. The bug-report
  text is treated as data, never executed.
- **Executing model output — honest scope.** When `verify_fix = TRUE`, `fix$code`
  runs in a fresh `callr` process with a `timeout`, **always** — never in-process,
  even when `x$backend == "inprocess"`. This isolates **R session state** (options,
  globals, infinite loops, crashes) from the caller; it is **not an OS sandbox**:
  the subprocess has the user's full filesystem, network, and privileges, so a
  verified fix may still perform arbitrary side effects. While minex already runs
  untrusted code by design, `fix$code` is a **distinct, higher-risk source**:
  model-invented code, *influenced by* the untrusted snippet (so steerable by
  injection), auto-run *without prior user approval*, and able to execute logic the
  original never reached (reduction truncates statements after the failure point).
  The prompt-injection framing constrains the response *shape*, not the *content* of
  `fix$code`, so it is not itself an execution control. Layered mitigations:
  (a) `verify_fix = FALSE` opts out of all execution; (b) a **heuristic denylist** — if `fix$code` contains an
  obvious side-effecting call (`system`, `system2`, `shell`, `pipe`, `download.file`,
  `url`, `socketConnection`, `unlink`, `file.remove`, `writeLines`, `write.csv`,
  `write.table`, `saveRDS`, `readRDS`, `save`, `load`, `source`, `sink`,
  `install.packages`, `Sys.setenv`, `Sys.getenv`), `explain_failure()` skips
  auto-execution and sets `fix$verified = NA` with
  `verification = "not auto-run: contains a potentially side-effecting call; run
  manually to verify"`. The denylist is **defense-in-depth, not a guarantee** — a
  source-text heuristic over a non-exhaustive call list that can be evaded (aliasing,
  `do.call`, `eval(parse())`); it reduces accidental and obvious-malicious I/O but is
  not a security boundary. All of this is documented on `explain_failure()`.
- **Cost/latency.** Exactly one model call per `explain_failure()` (structured output
  returns all requested sections at once); fix-verification adds at most one local
  execution. Documented so callers aren't surprised.

## Error handling

- Missing `ellmer`/`chat` → stop early with setup guidance (before any work).
- Model/network error → surface a clear condition; no partial object.
- Malformed structured output that fails type validation → `ellmer` retries per its
  contract; on persistent failure, error rather than return a half-parsed object.
- `explain_failure()` on a `minex_result` with no recorded `target` (custom-oracle runs)
  → the "why/fix" still work from code+condition, but `fix$verified = NA`
  (unverifiable — the oracle is not stored on the result), with `fix$verification`
  saying so. No "ran cleanly" substitute, which could contradict a non-error
  failure definition.

## Testing plan (TDD)

Write tests first, per unit:

- `build_prompt()` — includes the minimal code, the error message/class, requested
  modes; frames code as data (injection guard); honors `session_info`.
- `explanation_type()` — the structured schema matches the object fields.
- parse step — maps structured output → `minex_explanation` fields; unrequested
  modes are `NULL`.
- `verify_fix` — clean-run fix → `verified = TRUE`; fix that still errors with the
  **same** target → `FALSE`; fix that errors with a **different** error → `FALSE`
  (not a pass); for a warning/message target, a fix that silences it but raises a
  fresh error → `FALSE`; unobservable run → `NA`; `verify_fix = FALSE` → `NA`, no
  execution; custom-oracle result → `NA`. Assert it always runs via `callr`.
  **Split guard:** a multi-statement fix whose first line is a benign
  `library()`/assignment and whose later line still fails → `verified = FALSE`
  (proves `split_statements()` runs before `run_code`, not just the first expression).
  **Type-resolution:** a `condition = "any"` result that resolved to a warning →
  verification pivots on the resolved warning type, not the literal `"any"`.
  **Parse guard:** a syntactically invalid `fix$code` (truncated / unbalanced
  brace) → `verified = NA`, `verification = "fix did not parse: …"`, and the object
  is still returned (no abort). **Clean-run definition:** a warning-target fix that
  now raises a fresh error → `FALSE` (not `NA`), confirming the cleanliness rule.
- denylist screen — a `fix$code` containing a side-effecting call (`system`, `pipe`,
  `download.file`, `writeLines`, `unlink`, …) is **not** auto-executed: `verified =
  NA`, with the denylist `verification` message, and no subprocess is spawned.
- Chat is used statelessly — two `explain_failure()` calls sharing one `chat` don't
  accumulate turn history (assert via a stub that records call count / fresh state).
- `print`/`format`/`as.character` — stable, readable output; `as.character` yields
  the bug report.
- guards — non-`minex_result` `x` errors; missing `ellmer`/`chat` errors early;
  custom-oracle result yields `verified = NA`, not a fabricated pass.
- one `skip_on_cran` live integration test.

## Open decisions (defaulted; change if desired)

- **Name:** `explain_failure()`. The bare verb `explain()` was rejected — it
  collides with the widely-used `dplyr::explain()`/`dbplyr` S3 generic, and minex
  keeps those in `Suggests` at most, so masking is not an option. `explain_failure()`
  keeps the "explain" semantics, is minex-namespaced, and avoids the clash;
  `diagnose()` remains an acceptable alternative if preferred.
- **`session_info` default `TRUE`:** a real bug report needs it; toggle to `FALSE`
  for privacy.
- **`verify_fix = TRUE` by default — decided: keep on, with the denylist.**
  Maintainer-confirmed after weighing the security reviews. Rationale: `minex()`
  *already* executes the untrusted input by default during reduction, so
  auto-running the fix does not fundamentally change minex's execution posture — an
  attacker who controls the input already has direct execution via `minex()` itself,
  making the LLM detour a strictly weaker path than just embedding the payload in
  the script. The one genuinely new vector is an injection string in a *surviving
  comment/string literal* steering the model to emit a payload, which requires
  attacker-controlled input **and** model compliance **and** denylist evasion; the
  more practical (non-malicious) risk is a well-intentioned fix doing unexpected I/O,
  which the denylist blunts. Accepted tradeoff: keep `TRUE` + denylist, fully
  disableable via `verify_fix = FALSE`, and **document the threat model plainly** on
  `explain_failure()` — `callr` isolates R session state, not the OS; use
  `verify_fix = FALSE` for input you would not run yourself. (`diagnose()` /
  default-`FALSE` remain on record as the roads not taken.)
