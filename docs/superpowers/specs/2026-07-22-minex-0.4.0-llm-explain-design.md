# minex 0.4.0 design spec — LLM explanation of the minimal example

Date: 2026-07-22
Status: draft for review
Milestone: 0.4.0 (third of three: 0.2.0 core [done], 0.3.0 HDD [done], 0.4.0 LLM)
Depends on: 0.2.0 (run_code, matcher, minex_result), 0.3.0 (granularity = "expression")

## Goal

After minex reduces a failing script to its minimal reproducing snippet, add an
optional step that hands that snippet to a language model and returns a
structured, four-part account of the failure:

1. **Explain** — why the snippet fails, in plain English.
2. **Fix** — a corrected version of the snippet, *verified by executing it*.
3. **Bug report** — a paste-ready reproducible-example report.
4. **Diagnose** — the failure category and the R concept involved.

The LLM only ever sees the already-minimal snippet plus the recorded failure, so
no large-file encoding (graph/NN) is needed: reduction has already done the work
of making the input small and focused.

## Non-goals

- The LLM does **not** replace minex's oracle. "Does a reduction still reproduce?"
  remains a runtime fact proven by execution; the LLM is advisory only.
- No change to the deterministic reducer (`minex()`, `ddmin()`, HDD). This feature
  is a strictly additive, opt-in second step.
- No hard dependency on any LLM provider or on `ellmer`. Core minex keeps
  `Imports: callr` only; the LLM feature is entirely `Suggests`-gated.
- No rexgraph / relational-complex / hypergraph-NN integration (evaluated and set
  aside: the input is already minimal, and that stack is not CRAN-compatible).

## Architecture

### New function: `explain()`

Separate from `minex()` so the reducer stays pure and deterministic (a network
call must not enter the core reduction path, nor pollute `minex_result`).

```r
explain(x,
        chat = NULL,
        verify_fix = TRUE,
        timeout = 60,
        session_info = TRUE,
        modes = c("explain", "fix", "report", "diagnose"))
```

- `x` — a `minex_result` (carries `code`, `target$message`, `target$classes`,
  `condition`, `backend`). **No character-vector overload in 0.4.0** (YAGNI):
  `explain()` pairs with `minex()`, whose output is a `minex_result`. `x` is
  validated as such and `explain()` errors otherwise.
- `chat` — an injected `ellmer` Chat object (dependency injection; no vendor
  hard-wired). When `NULL`, read `getOption("minex.chat")`; if still absent, stop
  with actionable setup guidance. Works with any `ellmer` backend — local
  (`chat_ollama()`) or cloud.
- `verify_fix` — when `TRUE` (default), execute the model's proposed fix in a
  fresh **`callr`** process (never in-process) and record whether it produces a
  clean run. `FALSE` disables all code execution (pure suggestion).
- `timeout` — seconds allowed for the sandboxed fix execution (default `60`).
  `minex_result` does **not** store a timeout, so `explain()` owns this rather
  than reading a nonexistent `x$timeout`.
- `session_info` — include `utils::sessionInfo()` in the bug report (default
  `TRUE`; a real bug report needs it, but it can be omitted for privacy).
- `modes` — subset of the four sections to request (default all four).

Returns a `minex_explanation` S3 object.

### Data flow

```
minex_result  ->  build_prompt(x, modes, session_info)
              ->  chat$chat_structured(prompt, type = explanation_type())   # ellmer
              ->  parse into minex_explanation fields
              ->  if verify_fix && "fix" in modes: run_code(fix$code, backend="callr",
                    timeout=timeout) -> fix$verified   # always callr, never in-process
              ->  assemble bug_report markdown
```

### The `minex_explanation` object

An S3 list with `print`, `format`, and `as.character` methods (mirroring
`minex_result`; `as.character` returns the bug-report markdown):

| Field | Type | Content |
|-------|------|---------|
| `explanation` | chr(1) | why the snippet fails |
| `diagnosis`   | list   | `category` (chr), `concept` (chr), `severity` (chr) |
| `fix`         | list   | `code` (chr), `rationale` (chr), `verified` (lgl or NA), `verification` (chr: what running it did) |
| `bug_report`  | chr(1) | assembled markdown (repro + error + explanation + optional sessionInfo) |
| `model`       | chr(1) | model/provider string from the Chat, for provenance |
| `modes`       | chr    | which sections were requested |

Sections not requested in `modes` are `NULL`. `fix$verified` is `NA` when
`verify_fix = FALSE`, when the fix run can't be observed, or for custom-oracle
results (see Fix verification for the full three-valued rule).

### Structured output, not prose parsing

The model is asked for a typed object via `ellmer`'s structured-output support
(`type_object()` / `chat_structured()`), so fields arrive already separated and
validated — no regex scraping of free text. This satisfies the project rule to
validate LLM outputs at the boundary. `build_prompt()` and `explanation_type()`
are small, independently testable helpers.

### Fix verification (the differentiator)

When a `fix` is requested and `verify_fix = TRUE`:

1. **Always** run `fix$code` through `run_code(fix$code, backend = "callr", timeout = timeout)`.
   Model-generated code is *never* executed in-process, regardless of `x$backend`:
   the in-process path has no isolation and no timeout (`R/oracle.R`), so it is
   unsafe for unvetted LLM output. `explain()` pins `callr` here unconditionally.
2. Decide `fix$verified` (three-valued, and **strict** — `TRUE` means "the fix
   works", not merely "the original error changed"):
   - `TRUE` only on a **clean run**: the fix is `observed` AND produces **no
     condition of the target's type at all** (for an `"error"` target: no error;
     for `"warning"`/`"message"`: none of that type). A clean run is the only
     honest basis for pasting a fix into a bug report as "verified".
   - `FALSE` if the run still yields a condition of the target's type — whether the
     *same* failure (`verification = "same failure still present"`) or a
     *different* one (`verification = "different error: …"`). A different error is
     **not** a pass.
   - `NA` if execution can't be observed (timeout/crash → `observed = FALSE`), with
     an explanatory `verification`. Never fabricate a check.
3. **Custom-oracle results** (`x$target = NULL`): the user's failure was defined by
   a function that `minex_result` does not store, so there is no reproducible check.
   Set `fix$verified = NA` with `verification` stating the oracle was not captured.
   Do **not** substitute a "ran cleanly" pass — a custom oracle may define failure
   as a non-error property (wrong value, specific warning), so cleanliness could
   contradict the user's actual definition.

This reuses 0.2.0 `run_code` verbatim; the only new choice is pinning `callr`.

## CRAN and testing

- `ellmer` (and any provider package) go in **`Suggests`**. `explain()` guards with
  `requireNamespace("ellmer")` and errors with install guidance if absent.
- **Every test that touches `ellmer` begins with `skip_if_not_installed("ellmer")`.**
  This includes the prompt/parse/pipeline tests and `explanation_type()` — the type
  helper builds a real `ellmer` type object, so it needs `ellmer` *installed* even
  when the Chat is stubbed. The stub replaces the *network/provider*, not the package.
- **Injectable Chat → deterministic tests.** Tests pass a *stub* Chat object whose
  `chat_structured()` returns canned structured data, so the prompt→parse→assemble→
  print pipeline runs with **no network and no API key**.
- **Fix-verification tests** exercise the real `callr` path (the only path `explain()`
  uses): a known-good fix (clean run) → `verified = TRUE`; a fix that still errors
  (same or different error) → `FALSE`; a `verify_fix = FALSE` / custom-oracle /
  unobservable case → `NA`. `callr` is already an `Imports` dependency, so these run
  everywhere; the slow ones may be `skip_on_cran()`.
- Examples that need a real model are wrapped in `\dontrun{}`. One live
  round-trip test is `skip_on_cran()` + skipped when no model is configured.
- Spelling: add any new technical words to `inst/WORDLIST`.

## Prompt design and safety

- **Prompt-injection defense.** The reduced code is untrusted input. The system
  prompt frames it explicitly as *data to analyze, not instructions to follow*,
  and the structured-output contract constrains the response shape. The bug-report
  text is treated as data, never executed.
- **Executing model output.** The only code ever run is `fix$code`, and only when
  `verify_fix = TRUE`, **always** in a fresh `callr` process with a `timeout` —
  never in-process, even when `x$backend == "inprocess"` (an infinite loop or side
  effect in unvetted LLM code must not reach the caller's session). `verify_fix =
  FALSE` removes execution entirely. This caveat is documented on `explain()`.
- **Cost/latency.** Exactly one model call per `explain()` (structured output
  returns all requested sections at once); fix-verification adds at most one local
  execution. Documented so callers aren't surprised.

## Error handling

- Missing `ellmer`/`chat` → stop early with setup guidance (before any work).
- Model/network error → surface a clear condition; no partial object.
- Malformed structured output that fails type validation → `ellmer` retries per its
  contract; on persistent failure, error rather than return a half-parsed object.
- `explain()` on a `minex_result` with no recorded `target` (custom-oracle runs)
  → the "why/fix" still work from code+condition, but `fix$verified = NA`
  (unverifiable — the oracle is not stored on the result), with `fix$verification`
  saying so. No "ran cleanly" substitute, which could contradict a non-error
  failure definition.

## Testing plan (TDD)

Write tests first, per unit:

- `build_prompt()` — includes the minimal code, the error message/class, requested
  modes; frames code as data (injection guard); honors `session_info`.
- `explanation_type()` — the structured schema matches the object fields.
- parse step — maps structured output → `minex_explanation` fields; unrequested
  modes are `NULL`.
- `verify_fix` — clean-run fix → `verified = TRUE`; fix that still errors with the
  **same** target → `FALSE`; fix that errors with a **different** error → `FALSE`
  (not a pass); unobservable run → `NA`; `verify_fix = FALSE` → `NA`, no execution;
  custom-oracle result → `NA`. Assert it always runs via `callr`, never in-process.
- `print`/`format`/`as.character` — stable, readable output; `as.character` yields
  the bug report.
- guards — non-`minex_result` `x` errors; missing `ellmer`/`chat` errors early;
  custom-oracle result yields `verified = NA`, not a fabricated pass.
- one `skip_on_cran` live integration test.

## Open decisions (defaulted; change if desired)

- **Name:** `explain()` (alternative considered: `diagnose()`). `explain()` reads
  well as the verb paired with `minex()`.
- **`session_info` default `TRUE`:** a real bug report needs it; toggle to `FALSE`
  for privacy.
